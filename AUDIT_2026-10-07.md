# sniperBTC final audit (2026-10-07)

Audited code: branch `sniperbtc` at `a947faa` plus the fixes listed below. This is paper, replay and simulated-venue work only: no real order was placed, and no `.env` value was read or printed (key names only).

Method: every claim below comes from code that was run. Expected values in the new tests are computed by the tests themselves (Decimal/Fraction re-implementations of each rule), never by the production function under test. Each defect was reproduced before it was fixed, and one suspected defect (D3) did not reproduce and is recorded as such.

## 2. Findings reported, not changed (they need your decision)

| ID | Sev | Finding | Evidence |
| --- | --- | --- | --- |
| F1 | MEDIUM | **Share limits are enforced on a decision-time estimate.** The sniper's IOC is signed as a dollar amount (makerAmount in USDC, as live), sized for the share target at the decision's levels. If the ask falls before the match, the stake buys **more shares than the target**: a 10-share target at $5 filled 16.67 shares when the ask fell from 0.50 to 0.30. So the round side cap, the canary's shares-per-order cap and the target can be exceeded by one order's price improvement. The next order sees the real count and is refused. Capping actual shares would mean share-sized limit orders, a change to the execution you asked to keep. | `Execution.test_FINDING_a_dollar_ioc_buys_more_than_its_target_when_the_ask_falls`. In the stress run, 276 fills ended above target and the largest round went 18.5 shares over its side cap, with harness books that jump far more than real ones. |
| F2 | MEDIUM (scaling) | **The ledger rewrites its whole file on every fill**: 1.8 ms at 100 positions, 14 ms at 5,000, 60 ms at 20,000, on a worker thread under the ledger lock. It is off the decision and send path, but it delays booking. Live, it also delays the authorization save after a send. Recommendation: archive settled positions (or append-only journal plus snapshots) before the ledger reaches several thousand positions. | `bench_loop_costs.py` |
| F3 | MEDIUM (live) | **Canary caps are per process**: orders, fills, spend, rounds and session loss all reset on a restart. A crash-restart loop (systemd `Restart=always`) would re-arm the spend cap each time. Run the canary by hand, or cap restarts. | Read from `CanaryLimits` / `LiveExecution.session_start` |
| F4 | LOW | A second live install on the **same wallet** is refused only if its lock is listed in `OTHER_BOT_LOCKS`. Otherwise the safety net is live reconciliation: a confirmed fill that no order of ours explains halts the canary (`reconcile_once`). | Read |
| F5 | LIVE-VALIDATION | The chain-first settlement maps payout slot *i* to the CLOB's `tokens[i]`. That was verified empirically by an earlier session (12 + 9 rounds), not by a contract guarantee. A wrong order would invert settlements. Suggestion: once the mirrors resolve, compare the chain result against them and alarm on any difference. | `onchain_resolution.py` docstring |
| F6 | INFO | 20 `except Exception: pass/continue` sites in production code. All are on journals, telemetry, diagnostic probes, closing handles, or a batch-RPC fallback. None is on orders, fills, accounting or settlement. There is no bare `except:` (a test enforces this). | AST scan, `ErrorHandling` test |
| F7 | INFO | Without a terminal, an exception in the dashboard snapshot ends the status lines (trading continues: only the sniper task's death ends a run). | Read `_dashboard`, `_wait_until_stopped` |

## 8. Settlement

Lifecycle ACTIVE → EXPIRED → PENDING SETTLEMENT → SETTLING → SETTLED, with REDEEM PENDING → REDEEMED proven from the wallet balance (live only; paper is "N/A (PAPER)"). Tested:
- multiple markets pending while another trades;
- duplicate notifications and settle() called repeatedly: P/L counted once;
- API failure and non-final results never settle;
- a hung RPC never blocks the loop (worst loop step under 50 ms);
- a late fill re-settles with the same result.

Real chain timing was measured earlier: payout on chain about 58 s after expiry, the market socket's `market_resolved` at 123 s, Gamma at about 290 s, the CLOB later still. Real redemption timing **requires live validation**.

## 9. Restart and crash

Persisted: the ledger (fills; settlement; live authorizations), the paper account, journals, the settlement journal.

In memory only, so lost on restart:
- carry (restarts at 0, which is conservative);
- per-side cooldown;
- manager histories and UNKNOWN orders (paper only);
- canary counters (F3).

Round caps are restored from the ledger (R1). A live order whose fill is in the venue but not the ledger is recovered by `_recover_startup_fills` before trading (existing tests). Crash consistency: `record_fill_durable` and `settle` persist atomically and roll back on a failed write (existing tests).
