# Repair 2026-10-14: technical report

Branch `repair/2026-10-14` against the backup `fd916fb` (oct10 `main`, tag
`backup/pre-repair-2026-10-14`). Everything here was measured offline, with no
venue, wallet or network: a fake HTTP/2 CLOB, throwaway signing keys, and
copies of real state. **Nothing was pushed or deployed, and no real order was placed.**
Deployment, migration and rollback steps are in `DEPLOY_2026-10-14.md`.

## 1. Verdict

**Ready for a controlled live verification by the operator**, with the canary
($20 worst-case loss budget, its share caps) and a small wallet. **Not ready for
unattended size.** Two things only the live venue can show:

1. Whether the matching engine fills a FAK limit order by its **share** size.
   The contract bounds dollars strictly. A larger fill trips the kill switch
   (section 4).
2. Real fill rates and latency from the VPS. Paper's competition model is optimistic
   (section 11).

The strategy is unchanged. The same signals qualify, on the same side, at the
same cap and fair value, which the replay confirms (section 6). Every risk limit is the same or
stricter.

## 3. Strategy preserved

- The decision gates (trigger, window, cooldown, fair value and margin, Kelly, caps,
  freshness, backlog) judge the same dollar order as before. F1 changes only the
  order that is then signed. The frozen spec is unchanged except for
  `order_sizing = shares`.
- No risk limit was loosened. Changes went only toward stricter: the worst case is reserved
  (shares × limit + fee bound, never the estimate); unknown outcomes keep their
  reservation; previous-run orders keep the halt until the venue proves them.
- Not applied, awaiting the operator: fair margin 0.015 (branch
  `proposal/fair-margin-1.5c`), the step-up ladder, and exact-share gates.

## 5. Dollar eligibility vs share execution

- **Reservation**: exact. The signed worst case (shares × limit) plus a fee bound
  that covers the venue's own fee is reserved at prepare time, and only proven
  outcomes release it (60 random orders, UP and DOWN in flight together).
- **$20 canary loss budget**: it counts realized loss, plus open basis, plus every
  uncertain reservation, at the worst case and with no hedge credit. Because F1 reserves shares × limit
  (≥ the old dollar amount), the budget fills **sooner**, which is conservative.
- **Kelly**: the target is in shares and the order buys exactly it. A dollar
  FAK could under-buy when the price walked: replay #4 bought 190.5 vs 195 shares.
- **Carried inventory**: exact share counts, so later Kelly follow-ons can differ by
  ±1 share from the backup's.
- **Exposure limits**: share caps are now hard limits, not estimates. Dollar caps
  reserve the worst case.

The repair costs **+0.1 ms p50 / +0.4 ms p99** on an empty session, almost all of it

## 8. uvloop

There is no Linux host here (this machine is Windows, where uvloop does not run), so
**no gain has been shown and it stays off**. It is opt-in and paper only:
`SNIPER_UVLOOP=1`; `--live` refuses it; asyncio's loop is used if uvloop is
missing. To decide on the VPS:

```bash
pip install uvloop && python bench_execution.py --json a.json && python bench_execution.py --uvloop --json b.json
```

Enable it only if signal-to-wire p99 and loop lag improve with no new skips or errors. The live
gate then needs a reviewed change.

## 9. Crash recovery, migration, rollback (copies of production state)

- **Ledgers** from `/opt/btcbot` (live 48 positions / 53 lots / 54 authorizations;
  sniper, adds, multi) load identically under backup and repair. The repair
  extends, saves and reloads them, and the backup reads the result identically.
- **Canary state** v2 → v3: counters carried over (3 orders, 2 fills, $12.50,
  1 round) and `.v2.bak` kept.
- **Rollback, ledger**: after a crash the backup refuses a journal holding
  `authorize` entries. This fails closed. `ledger_compact.py` (with the repaired
  code) fixes it: verified on the real ledger copy, identical afterwards.
- **Rollback, canary**: the backup refuses v3 even with `--new-canary-session`.
  With the v3 files moved aside, restoring `.v2.bak` reopens the exact counters, or a
  new session starts. Both verified.
- **Crash points** (scenarios 16–18):
  - Before the intent is durable: nothing is sent.
  - After the intent but before the send: the restart halts. The venue has no record
    of the order, and no record is not proof, so the halt stays for a manual check.
  - After the send but before the reply: a match that is booked, or a proven zero
    fill, resolves it; anything else keeps the halt.

  Nothing is ever resent.

## 11. Remaining risks

1. **Engine share bound unverified** (section 4). Watch the first live fills; the
   kill switch halts on a breach.
2. **Paper is optimistic.** Its competition model cannot see other takers'
   speed. Live fill rates will be lower.
3. **Binance futures backlog skips.** The default count gate still refuses
   fresh bursts. The fix is behind flags, off, and refused live, pending review.
4. **Restart reconciliation needs an order hash.** Orders sent by the backup
   carry none, so a crash under the old code still needs a manual reconcile.
5. **uvloop is unmeasured on Linux** (section 8).
6. **Replay coverage is small**: 7 decisions on one day's Binance recording.
   It shows equivalence, not profitability.
7. **Windows timings are not VPS timings.** fsync dominates the backup's numbers
   here; the VPS (ext4 SSD) is faster for both, and the ratios matter more than the absolutes.
8. **Geoblock**: orders need a VPS in an allowed region (AMS3 / IE are API-allowed;
   GB and KR are blocked).
9. **A start-up halt can need you.** After a crash, an order the venue has no
   record of (never sent, or not yet indexed) keeps the halt beyond the ~4 minute
   lookup. Check the wallet's orders and trades on Polymarket. If nothing is
   open, move the canary state files aside (keep them) and start with
   `--new-canary-session`. The bot refuses a new session while an unresolved
   intent is in the state, on purpose. Never edit the state by hand.
10. **One stall at 20,000 positions.** In the repaired benchmark one order took
    142 ms (p99 12.7 ms). Watch loop lag on the dashboard as the ledger grows.

## 12. Recommended live verification

Follow `DEPLOY_2026-10-14.md` sections 3–5: a clean stop of any other bot on the
wallet, a state backup, the tests on the VPS, then paper for one or more rounds, then
