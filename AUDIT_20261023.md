**There is no `single_execute` function** in this repository; every module was searched. The
single-order path audited in its place is:

`Sniper._signal → _fire_now → _decide → _fire_live → LiveExecution.prepare → LeanSender.prepare (sign)
→ start_send / LeanSender.start (durable intent, write) → LiveExecution.send → LeanSender._send_once →
_classify → _after → LiveExecution._authorize → user channel (FillStore) → fill_for / _fak_fill →
reconcile_once → ledger booking → settlement`.

Severity: CRITICAL = losses, unintended or duplicate orders, or a serious execution failure. HIGH = missed
trades, failed orders, inconsistent state. MEDIUM = incorrect handling, degraded performance or
intermittent errors. LOW = minor or maintainability.
Status: CONFIRMED = reproduced or shown in the records. CODE = certain from the code, never seen in the
records. SUSPECTED = not verified; what is missing is stated. DESIGN = works as written, but the effect
is a risk the operator should decide on.

**Not a bug (market behaviour / calibration):**
- Live keeps winning a little **less often than fair predicts**: 332 vs 351.6 expected 10-15 → 10-21 (z ≈ −1.7), and 48 vs 50.2 on 10-21 → 10-22.
- The fair model overstates by about the edge it claims. That's adverse selection: we get filled when the market knew better.

- These are calibration questions, not code defects.
- `kelly_shares` was checked against the binary Kelly optimum and is correct.
- The anchored fair value and `fair_limit` match their documentation.
