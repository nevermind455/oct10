# Deploying the 2026-10-14 repair: dependencies, migration, rollback

Branch `repair/2026-10-14`, built on `fd916fb` (oct10 `main`; tag
`backup/pre-repair-2026-10-14`). Not pushed and not deployed: both wait for the
operator. What changed and the measurements are in `REPAIR_2026-10-14.md`.

The steps below never place an order. The first live run is the operator's
controlled verification (section 5).

## 1. The package

`archive/deploy-2026-10-14/` (gitignored, local only):

| file | what |
|---|---|
| `sniperBTC-repair-2026-10-14-<commit>.tar.gz` | `git archive` of the branch: tracked source only, no `.env`, no state, no journals, no zip |
| `SHA256SUMS` | checksum of the tarball |
| `VERSION` | the commit, its parent chain back to `fd916fb`, the date |

You can also deploy with git once the branch is pushed (that needs your go-ahead):
`git fetch && git checkout <commit>` in the install directory.

## 2. Dependencies

There are no new required packages. The pins are in `requirements.lock.txt`
(Linux, Python 3.12):

- **Python 3.12** is the tested Linux version. 3.13 also passes on Windows.
  Avoid 3.14 for now: `coincurve` 21 does not build on it. Use `uv python install 3.12` if the
  system Python is 3.14.
- **py-clob-client-v2 1.2.0** is pinned. The F1 signing tests pass under both
  1.1.0 and 1.2.0. 1.2.0 only adds an Exchange V3 route, which this bot does not use;
  it signs on the V2 domain (`domain_version` "2") either way.
- **uvloop** is optional and not installed by default. It is not in the requirements.
  `SNIPER_UVLOOP=1` is paper-only, and `--live` refuses to start with it, until
  `bench_execution.py --uvloop` on the VPS shows a gain without regressions.

```bash
python3.12 -m venv .venv && . .venv/bin/activate && pip install -r requirements.lock.txt
```

## 3. Before switching

1. **One bot per wallet and ledger.** Stop the running bot cleanly first (Ctrl+C,
   or `kill -TERM`). A clean stop drains late fills and leaves a compact ledger
   snapshot. Never start this version while `/opt/btcbot`'s bot (or any other)
   trades the same wallet or ledger. The process locks refuse a second bot on
   the same machine, but they cannot see another machine.
2. **No order in flight.** With the old bot stopped, the old (v2) canary state
   must list no unresolved order:

   ```bash
   python3 -c "import json; d=json.load(open('live_canary_state.json')); print([k for k,i in d.get('intents',{}).items() if i.get('status') in ('DISPATCHING','ACCEPTED','AMBIGUOUS')] or 'no unresolved orders')"
   ```

   The new code reconciles a previous run's unresolved orders by order hash at
   start (section 4). Orders sent by the OLD code carry no hash, so they keep
   the start-up halt and still need a manual reconcile, just as before.
3. **Back up the state directory**, with everything beside the ledger:

   ```bash
   tar czf ~/state-before-repair-$(date -u +%Y%m%dT%H%M%SZ).tgz live_ledger.json* live_canary_state.json* live_sniper.jsonl
   ```

   (Use your `LEDGER_PATH` name if it differs. The canary state always sits next to
   the ledger as `live_canary_state.json`, unless `SNIPER_CANARY_STATE_PATH` is set.)
4. **Run the tests on the VPS** in the new install. Neither command needs a network,
   a wallet or `.env`:

   ```bash
   python run_tests.py && python run_scenarios.py
   ```

   Expect `43/43 suites passed`. On Linux the scenario run also executes the
   POSIX-only directory-fsync test, which is skipped on Windows.

## 4. Migration (automatic, on the first start)

| state | what happens | kept for rollback |
|---|---|---|
| canary session `live_canary_state.json` v1/v2 | migrated to v3: a small header, append-only journal segments (`.journal.<k>`) and an archive of finished intents (`.archive.jsonl`); the counters are carried over exactly | `live_canary_state.json.v2.bak` (byte copy) |
| ledger `live_ledger.json` | the same snapshot format, read as is; new authorizations are journaled (`{"op": "authorize"}` in `.journal`), not full rewrites | the snapshot itself; see 6.2 |
| unresolved orders from a previous run | looked up on the venue by their order hash for up to about 4 minutes. A proven zero fill is released; a match whose trades are booked is confirmed; anything else keeps the start-up halt | nothing is resent |

Verified on copies of the real state from `/opt/btcbot`: 48 positions, 53 lots,
54 authorizations, plus the sniper, adds and multi ledgers. All of them load
identically under the old and the repaired code. The repaired code extends,
saves and reloads them, and the old code reads them back identically. A v2
canary state migrates with its counters (3 orders, 2 fills, $12.50, 1 round)
and its `.v2.bak`.

### New settings

All are optional, and all default off or unchanged:

| variable | default | live |
|---|---|---|
| `SNIPER_ORDER_SIZING` | `shares` | Live requires `shares`: a FAK spends its whole shares × the cap and a cheaper fill buys extra shares (logged, never a halt). `dollars` (the book cost) is for paper A/B only |
| `SNIPER_BOOK_QUIET` | `0` | opt-in. It takes a connected, gap-free feed's last book; keep it off for the verification |
| `SNIPER_BACKLOG_GATE` | `count` | `age` is refused |
| `SNIPER_FEED_COALESCE` | `0` | `1` is refused |
| `SNIPER_UVLOOP` | `0` | `1` is refused |

The frozen spec is unchanged except for `order_sizing = shares` (since 2026-10-15). A FAK spends its whole shares × the cap and is sent as a dollar order. `--live`
still refuses any other resolved value.

## 5. Controlled live verification (the operator's)

1. Start paper first on the VPS for one or more rounds: `python run.py --paper --dash`.
   Check that the dashboard shows the feeds, `NET`, and the prepared next round before each boundary.
2. Live with the canary and a small wallet:
   `SNIPER_LIVE_CANARY=1 python run.py --live --dash`.
   Leave the canary's defaults alone ($20 worst-case loss budget, per-order share cap).
3. Watch the first orders in `live_sniper.jsonl` (or `python live_check.py`).
   Each order's cost must never exceed its `amount` (the signed dollars); if it
   does, the kill switch halts. A falling ask can buy more shares than the
   target; that is journalled as `over_target`, as before the repair.
4. Stop at the first halt and read its reason. Do not delete the state to get going again.

### Clearing the 2026-10-14 "filled above its signed size" halt

That halt came from the withdrawn share-sized order (the report's section 0).
The 180s halt after it was the same order; the new code halts once per order.
The CLOB answered null for that order's id (2026-10-15), so a restart cannot settle
it from the venue's order record. The evidence instead is the order's trades (by
`taker_order_id`), booked in the ledger, which must be exactly the trades the reply named or,
when it named none (as here), add up to the reply's own totals (makingAmount $3.74,
takingAmount 12.896552). With the bot stopped:

1. `git pull`.
2. Check the order against Polymarket (read-only):

   ```bash
   .venv/bin/python reconcile_order.py 0xa1fa8479
   ```

   This compares the order's trades on the venue (deduplicated by trade id), and its
   record when the venue keeps one, against the reply's trade ids in the journal,
   the ledger's lots and the wallet's position. It needs `VERDICT: consistent`. If
   it prints `NOT YET`, stop here and keep the state; it lists what disagrees.
3. Settle the order's canary intent (writes only the canary state; nothing is sent):

   ```bash
   .venv/bin/python reconcile_order.py 0xa1fa8479 --settle
   ```

4. Start live as usual, adding `--new-canary-session`. The old canary state is kept
   as `.bak`, and the new session starts with no halts and a fresh $20 budget. It
   refuses to start while any order is still unresolved.

From this version on, the canary intent keeps the reply's trade ids and totals. A restart then
settles such an order by itself, without the venue's order record, once exactly those
trades are booked under its authorization.

## 6. Rollback to the backup (`fd916fb`)

### 6.1 Code

```bash
git checkout backup/pre-repair-2026-10-14
```

Or unpack your previous install. Stop the repaired bot first.

### 6.2 Ledger

- **After a clean stop**, nothing is needed: the journal is empty and the old code reads
  the snapshot.
- **After a crash or `kill -9`**, the journal may hold `authorize` entries, which
  the old code rejects: "exists but is unreadable or invalid; refusing to start".
  This fails closed and loses nothing. Fold the journal into the snapshot with the
  **repaired** code before switching:

  ```bash
  python ledger_compact.py live_ledger.json
  ```

  It takes the bot's own ledger lock, so it refuses while a bot runs. Verified on a
  copy of the real ledger after a simulated crash: the old code refused it, and after
  the compaction it loaded with identical positions, lots and authorizations.

### 6.3 Canary session

The old code cannot read v3, **even with `--new-canary-session`**. Move the
v3 files aside first:

```bash
mkdir -p repaired_canary_state && mv live_canary_state.json live_canary_state.json.journal.* live_canary_state.json.archive.jsonl repaired_canary_state/ 2>/dev/null
```

Then do one of these:

- **(a) The repaired bot sent no live order since the migration:** restore the backup.
  The old code then reopens the exact counters, as verified.

  ```bash
  cp live_canary_state.json.v2.bak live_canary_state.json
  ```

- **(b) It did send orders:** `.v2.bak` would understate today's risk. First
  confirm on the venue that no order is open or unresolved, then start a new
  budget: `python run.py --live --new-canary-session ...`. Verified: with the
  v3 files moved aside, the old code opens a new session.

### 6.4 Verify

Start the old code in paper mode against a copy of the state, or run
`python sniper_check.py`. The ledger counts must match those before rollback.
